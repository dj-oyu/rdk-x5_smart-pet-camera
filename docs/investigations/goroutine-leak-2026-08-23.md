# goroutine leak 調査 (2026-08-23)

リファクタ計画のレビューで挙がった2つの疑いを、着手前に切り分けたもの。
結論は **どちらも実害なし**。構造上の指摘は正しいが、leak にはなっていない。

## 疑い1: `convertToMP4` が待たれずに起動される

`internal/webmonitor/stream_recorder.go:168` と `:489` で

```go
go r.convertToMP4(filename, detectionOffset)
```

と起動され、呼び出し側は完了を待たない。

**判定: leak ではない。ただしシャットダウン時の欠損リスクはある。**

goroutine は変換完了とともに終了するので蓄積しない。問題は「プロセス終了時に
変換中だと MP4 が中途半端になる」点で、これは leak ではなく shutdown の
順序の問題。録画停止からプロセス終了までの間に ffmpeg が終わらなければ
起きるが、頻度と影響 (最後の1本が壊れる) から今回は対処しない。

## 疑い2: ブロードキャスタの Stop に WaitGroup がない

5つのブロードキャスタはいずれも `Stop()` が `close(stop)` するだけで、
`run()` goroutine の終了を待たない (broadcaster.go:100, 383, 705, 1070, 1245)。

**判定: leak ではない。Stop() が終了を待たないだけ。**

`run()` は `<-stop` を監視して return するので goroutine は確実に終わる。
`Stop()` が先に返るためシャットダウンとの競合はありうるが、goroutine が
残り続けるわけではない。

## 実測

構造の読みだけで終わらせず、稼働中の実機で測った。

### web_monitor — 購読者の後始末

SSE と MJPEG の接続・切断を 300 回繰り返し、RSS とスレッド数を観測:

| 時点 | RSS | Threads |
|------|-----|---------|
| 開始 | 32,340 KB | 19 |
| 100回後 | 33,928 KB | 19 |
| 300回後 | **31,768 KB** | **19** |

増加なし (むしろ GC で減少)。購読者の登録解除は正しく動いている。

web_monitor には pprof が無いため RSS とスレッド数での間接測定。
goroutine 数を直接見たい場合は pprof の追加が必要。

### streaming-server — pprof で直接

`:6060/debug/pprof/goroutine` を使用。`/offer` を 60 回叩いて観測:

| 時点 | goroutines |
|------|-----------|
| 開始 | 15 |
| 30回後 | 15 |
| 60回後 | **15** |

増加なし。セッションの後始末は正しく動いている。

## 結論

**leak は存在しない。** 構造上の指摘 (WaitGroup 不在、待たれない goroutine) は
事実だが、いずれも goroutine の蓄積には至らない。リファクタのブロッカーから外す。

残る改善余地は「シャットダウン時に変換中の MP4 が壊れうる」点のみで、
これは leak とは別の課題。
